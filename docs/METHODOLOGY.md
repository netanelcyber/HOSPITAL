# Wordfence Recon Methodology

This document explains what each `wfrecon` module tests, the signal it relies on,
and how to interpret findings during an authorized assessment. All checks are
non-destructive reconnaissance (GET/POST observation only).

## 1. fingerprint

Confirms Wordfence is present and, where possible, its exact version.

- **readme.txt** — `/wp-content/plugins/wordfence/readme.txt` exposes a
  `Stable tag:` line. Version disclosure enables precise CVE correlation.
- **Static assets** — CSS/JS under the plugin directory returning HTTP 200.
- **Block-page signature** — Wordfence's "your access to this site has been
  limited" / "Generated by Wordfence" pages.
- **WAF cookie** — a `wfwaf-*` cookie indicates an active firewall.

*Hardening:* block direct access to `readme.txt`, disable directory listing, and
consider Wordfence's option to hide the WordPress/plugin version.

## 2. waf

Measures whether the firewall is actually inspecting traffic and in which mode.
Sends **benign** strings that merely *resemble* attack signatures (SQLi, UNION,
XSS, LFI, RCE, a `WPScan` User-Agent) in query parameters only — they never reach
a vulnerable sink.

- All probes passing through while Wordfence is detected → firewall likely in
  Learning Mode, disabled, or Extended Protection not installed.
- Partial blocking → note which signature classes are uncovered.

*Hardening:* enable **Extended Protection** (`auto_prepend_file` →
`wordfence-waf.php`) and complete firewall optimization.

## 3. users

Username enumeration is the precursor to credential attacks Wordfence's Login
Security is meant to stop.

- **`?author=N`** — inspected with redirects disabled so the `Location:
  /author/<user>/` leak is visible.
- **REST API** — `/wp-json/wp/v2/users` returning author slugs.
- **Login error differentiation** — a single benign POST for an unknown user vs
  a known user with a wrong password; differing error text confirms valid names.
  (No brute forcing — exactly two requests.)

*Hardening:* enable "Prevent user enumeration" and disable/restrict the REST
users endpoint.

## 4. exposure

Looks for sensitive files that should never be world-readable:

- `wp-content/wflogs/` directory listing, `config.php`, `rules.php` — leaking
  these exposes firewall config and bypassable rules.
- `debug.log`, `wp-config.php.bak`, `wp-config.php~` — path/credential leakage.
- `.user.ini` — also used positively to confirm Extended Protection.
- `xmlrpc.php` — brute-force/pingback amplification surface.

*Hardening:* deny web access to `wflogs/`, remove editor/backup files, and block
`xmlrpc.php` if unused.

## 5. cve

Correlates detected plugin versions against the local, offline knowledge base in
`wfrecon/cve_db.py`:

- **Wordfence's own CVEs** (e.g. CVE-2022-3144 stored XSS ≤ 7.6.0) — a defender
  tool is still attack surface.
- **Actively-exploited ecosystem CVEs** such as **CVE-2025-11833** (Post SMTP
  unauthenticated account takeover, CVSS 9.8) — flagged because a WAF is not a
  substitute for patching.

`version_lt` treats a plugin as vulnerable when its installed version is below the
fixed version. When a version can't be determined, the entry is reported as
*unconfirmed* for manual review.

## Reporting

Findings carry a severity (`info`→`critical`), module, detail, evidence, and
references. Use `--json FILE` for machine-readable output suitable for pipelines
or a written report appendix.
