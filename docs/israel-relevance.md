# רלוונטיות למשק הבריאות הישראלי (Israel-Specific Annex)

**עודכן:** אוגוסט 2026
**מטרה:** מיפוי החולשות מהמסמכים האחרים לשוק הישראלי הספציפי — מה באמת מותקן כאן, ולמי מדווחים בישראל.

> **התובנה המרכזית:** המוסדות הגדולים בישראל (קופות החולים, בתי החולים) **אינם** משתמשים ב-OpenEMR/OpenMRS אלא במערכות **קנייניות**. לעומת זאת, שכבת ה-**FHIR/HL7** היא דווקא ליבת המערכת הישראלית ובעדיפות עליונה — בגלל **חוק ניוד המידע הרפואי** ו-**חילופי המידע הלאומיים (HIE)**.

---

## 1. דירוג רלוונטיות לישראל

### 🔴 עדיפות עליונה — שכבת HL7 / FHIR ואינטגרציה

**למה קריטי בישראל:** חוק ניוד המידע הרפואי (יולי 2024) מחייב **FHIR R4**, יעד יישום מלא **יולי 2029**. קיימים **חילופי מידע לאומיים (National HIE)** שכל הקופות ובתי החולים חייבים להתחבר אליהם — כל המידע הקליני זורם דרך שכבה זו. קהילת **FHIR-IL** (8400 The Health Network + משרד הבריאות + רשות החדשנות) מובילה את הלוקליזציה.

| מוצר | חולשות רלוונטיות | הערה ישראלית |
|---|---|---|
| **HAPI FHIR** | CVE-2026-34361 (SSRF 9.3 + גניבת טוקנים), 34360, 55471 (XXE), 45367 (ReDoS) | מימוש הייחוס ב-Java; סביר שמוטמע באינטגרציות FHIR ישראליות רבות. הרלוונטיות **גוברת** עם התקדמות היישום עד 2029. |
| **Mirth Connect** | CVE-2023-43208 (RCE לא-מאומת) | integration engine נפוץ עולמית וכולל בישראל |
| **dbMotion** | (ראו דפוס P4 — HIE כיעד ערך-גבוה) | פתרון HIE **ממקור ישראלי**, מוטמע בכללית. שכבת HIE = יעד תקיפה מרכזי |

### 🟠 עדיפות גבוהה — DICOM / PACS והדמיה

אוניברסלי; קיים בכל בית חולים ומכון הדמיה בישראל.

**הנוף הישראלי בפועל:**
- **Fujifilm SYNAPSE** — מארכב **מעל 25% מכלל בדיקות ההדמיה בישראל** (קופות, בתי חולים, עשרות מכונים פרטיים). ריכוזיות = יעד ערך-גבוה בודד.
- **Dinco** — הקימה את ה-**PACS הענני הראשון בישראל אצל מכבי**.
- **PacsSee** — PACS ענני לרדיולוגים ומכונים פרטיים.
- מכונים פרטיים, קליניקות מומחים, ומרפאות שיניים עם CBCT — כולם צמתי DICOM.

**איפה החולשות נכנסות — לרוב עקיף:** חלק מהחולשות שמיפינו הן בשכבת ה**ספריות** (GDCM, pynetdicom) שעשויות להיות מוטמעות בתוך מוצרים אחרים; אחרות הן ב**מוצר עצמאי** (Orthanc הוא שרת PACS עצמאי) או ב**כלי CLI ספציפיים** (חלק מממצאי DCMTK/pynetdicom). ⚠️ **אין להסיק ש-SYNAPSE או כל PACS מסחרי אחר יורש את החולשות האלה** — הטמעה בפועל של רכיב פגיע חייבת אימות דרך **SBOM או אישור הספק**, לא הנחה. החשיפה הישראלית דרך ספרייה מוטמעת אפשרית אך **טעונת הוכחה per-product**.

| וקטור | רלוונטיות ישראלית |
|---|---|
| **חשיפה לאינטרנט + ללא אכיפת AE Title** | הגבוה ביותר. PACS ענניים ומכונים פרטיים קטנים עם IT מוגבל = הסיכון הכי מוחשי. נתון גלובלי (99.56% ללא AE Title, 0.14% TLS) — לאמת ספציפית לישראל. |
| **ספריות מוטמעות (GDCM/DCMTK/OpenJPEG)** | עקיף — תלוי איזה SDK כל ספק מטמיע; memory-corruption חל על כל צומת שמקבל DICOM חיצוני. |
| **צפייני DICOM בתחנות** | MicroDicom/RadiAnt (ערוצי עדכון לא-מאומתים) אם בשימוש בתחנות רדיולוג. |
| **מכונים פרטיים קטנים** | החוליה החלשה — פחות תקציב אבטחה, לעתים חשופים ישירות, מרכזים PHI הדמיה רגיש. |

**המלצה מעשית:** (1) סריקת היקף חיצונית מורשית של IP ישראליים בפורטים 104/11112/4242/8042; (2) לדרוש מהספק (Fujifilm/Dinco/וכו') את גרסת ה-DICOM SDK ומדיניות הטלאים; (3) אכיפת AE Title + DICOM-TLS + סגמנטציה — יותר ערך מיידי מטלאי בודד; (4) לתעדף מכונים פרטיים כ-long tail חשוף.

### 🟡 עדיפות בינונית — ציוד רפואי מחובר (IoMT)

אותם מכשירים בדיוק נמכרים בישראל (Medtronic, Philips, מוניטורים, משאבות עירוי). Contec CMS8000, Eppendorf BioFlo 320 וכו' עשויים להימצא במתקנים ישראליים. הבקרות המפצות (סגמנטציה, ניטור) זהות.

### ⚪ עדיפות נמוכה למוסדות הגדולים — OpenEMR / OpenMRS

הקופות ובתי החולים = מערכות **קנייניות**, לא OpenEMR. הרלוונטיות מוגבלת ל:
- מרפאות פרטיות קטנות, מרפאות שיניים/וטרינריות, עמותות, וסביבות dev/test.
- לכן ניתוח ה-OpenEMR (SUSP-BIO-08/22, תבנית הדיווח) חשוב פחות בהקשר הישראלי — אך נשאר תקף היכן ש-OpenEMR כן רץ.

## 2. למי מדווחים בישראל (Reporting Channels — IL)

| גוף | מתי / איך |
|---|---|
| **מערך הסייבר הלאומי / CERT-IL** | ערוץ ראשי לאירועי סייבר. טלפון **119**, `report@cyber.gov.il`. יש מגזר בריאות ייעודי; מתאמים מול היצרן. |
| **אגף/מנהל הסייבר במשרד הבריאות** | לאירועים ולחולשות במוסדות בריאות תחת פיקוח המשרד. |
| **הרשות להגנת הפרטיות** | לחשיפת מידע רפואי (PHI). **תיקון 13** ותקנות אבטחת המידע מחמירים חובות. ⚠️ **הדיווח אינו אוטומטי לכל דליפה** — חובת ההודעה תלויה בכך שהאירוע עומד בקריטריון "אירוע אבטחה חמור" (רמת האבטחה של המאגר והיקף האירוע). יש לבצע את ההערכה עם גורמי פרטיות/משפט, לא להניח דיווח מחייב. |
| **היצרן / המתחזק** | ראשון בסדר הדיווח (ראו `suspected-cve-candidates.md` → יעדי דיווח + CNA). לגלובליים: GitHub CNA / CISA / MITRE. |

**סדר מומלץ בישראל:** יצרן/מתחזק ראשון → במקביל CERT-IL אם מדובר במערכת בתשתית בריאות ישראלית → הרשות להגנת הפרטיות **אם ההערכה קבעה שזה אירוע בר-דיווח** → הקצאת CVE דרך ה-CNA הרלוונטי (GitHub/CISA/MITRE).

## 3. שורה תחתונה לצוות הגנה ישראלי

1. **התמקדו בשכבת ה-FHIR/HL7 קודם** — זו נקודת הריכוז של המשק הישראלי ובעדיפות עולה מבחינה רגולטורית. הקשיחו/עדכנו HAPI FHIR (6.9.4+), אל תחשפו את ה-FHIR Validator, בדקו integration engines (Mirth 4.4.1+).
2. **מפו את חשיפת ה-PACS הישראלית** — סריקה חיצונית + אכיפת AE Title ו-TLS.
3. **הניחו שה-HIE הוא יעד** — dbMotion וכל צומת חילופי-מידע לאומי מרכזים PHI של אוכלוסייה שלמה; בקרת גישה ו-segmentation שם קריטיות.
4. **OpenEMR** — רלוונטי רק אם אתם מפעילים אותו בפועל (מרפאות קטנות/dev), לא לליבת המשק.
